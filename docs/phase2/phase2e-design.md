## 0. 結論の要約

作品は自作のノベルゲームで使う。本文（draft.md）を、ゲームのエンジンがそのまま読める**行形式の台本**にする。

Human の決定（2026-10-09）：

* 台本は行形式のテキスト（記号の行を機械的に解析する。人も AI も読み書きできる）
* 入れる機能：話者名、立ち絵の表情、立ち位置・登場と退場、選択肢と分岐
* 分岐は「章の中で分かれて合流する」規模（章ごとのルート分岐は入れない）
* 分岐の中で設定（呼び方・伏線・知識）が変わってよい。合流したあとは、**フラグ**で台本を書き分ける。フラグは次の章以降にも残る
* 表情は、変えるときだけ書く（次に変えるまで続く）
* エンジンは draft.md（行形式の Markdown）をそのまま読む。JSON の書き出しは作らない

方針は次の4つ。

1. **台本の解析器（parser）を Controller に作り、機械検査と Claude への資料がそれを使う。** 台本の形式の定義は、エンジンとの約束になる（`docs/script-format.md` として独立させる）。解析できない台本は、場面の区切りと同じく draft Job で FAIL にする（エンジンが読めないため）。
2. **話者が行の頭で決まるので、話者に依存する検査の一部を機械検査に移す。** 仕様 §11.3 の「台詞の話者は文字の照合では確定できない」は、台本形式では成り立たなくなる。Claude の検査は残す（一人称は語の照合だけでは判定しきれないため）。
3. **選択肢がフラグを立て、合流後の台本は `@if` で書き分ける。** フラグは作品全体で ID を持ち、次の章以降にも残る（§5）。設定の変化をフラグに結び付ける部分（規則表・伏線・状態更新をフラグごとに計算する）は大きいので、**2-F として分ける**。
4. **小説の形式も残す。** project.yaml で作品ごとに形式を選ぶ【決定 1】。既存の作品と試験を壊さないため。

段階（受入3・4 の試験が済んだ 2-D の後、2-D5 以降の range_edit などより前に行う。range_edit は台本の形式に依存するため）：

| 段階 | 内容 |
|---|---|
| 2-E1 | 台本の解析器、characters と plan の schema の拡張（純粋な関数と単体テスト） |
| 2-E2 | 台本の機械検査、draft の指示と draft Job の検査 |
| 2-E3 | validate への接続（規則表に表示名・表情、Claude のプロンプト） |
| 2-E4 | 分岐とフラグ（plan の場面のつながり、フラグの登録、`@if`、検査） |
| 2-E5 | 結合試験 |
| 2-F | フラグに結び付いた設定（規則表・伏線・知識・summary をフラグごとに扱う）。別に設計する |

## 1. 台本の形式

```text
<!-- scene: S1 -->
@bg 市場_昼
@enter C001 left 通常
@enter C002 right 笑顔
カイは港の市場で美咲を見つけた。
カイ［驚き］「美咲、こんなところで何してるんだ」
美咲「私は魚を買いに来たの。カイこそ、どうしたの」
カイ（言えるわけがない）
@face C002 通常
@exit C002
@choice
- 一緒に市場を回る -> S2 +market_together
- 船を見に行く -> S3
```

合流したあとの場面（フラグで書き分ける例）：

```text
<!-- scene: S4 -->
@if market_together
カイ「君と回れて楽しかった」
@else
カイ「美咲、船はすごかったぞ」
@endif
美咲「また明日ね」
```

行の種類（1行は必ずどれか1つ。空行は区切りとして無視する）：

| 行 | 形 | 意味 |
|---|---|---|
| 場面の区切り | `<!-- scene: S1 -->` | 今と同じ（§6.5.1） |
| 背景 | `@bg <背景名>` | 背景を変える |
| 登場 | `@enter <人物 ID> <left｜center｜right> [表情]` | 立ち絵を出す。表情を省くと、その人物の既定の表情 |
| 退場 | `@exit <人物 ID>` | 立ち絵を消す |
| 表情 | `@face <人物 ID> <表情>` | 台詞なしで表情を変える |
| 選択肢 | `@choice` と、続く `- <選択肢の文> -> <場面 ID> [+<フラグ>]` の行 | 場面の最後に置く。`+<フラグ>` はその選択肢を選んだときに立てるフラグ（§5） |
| 移動 | `@goto <場面 ID>` | 場面の最後に置き、合流先へ進む（§5） |
| 条件 | `@if <フラグ>`・`@if not <フラグ>`・`@else`・`@endif` | フラグで台本を書き分ける（§5）。入れ子にしない |
| 台詞 | `<表示名>[［表情］]「<台詞>」` | 話者と台詞。表情は変えるときだけ |
| 心の声 | `<表示名>[［表情］]（<内容>）` | 声に出さない言葉 |
| 地の文 | 上のどれでもない行 | ナレーション |

* 表示名は、characters/ の新しい欄 `display_name`（§2）。名前のない端役は、plan の場面の `extras`（§3）に挙げた名前を表示名として使う（立ち絵は持たない）。
* 人物の指定は、`@` の行では人物 ID、台詞の行では表示名。台本を人が読みやすくするため、台詞は表示名にする。表示名は作品の中で一意でなければならない（schema の semantics で検査）。
* `［］` と `（）` は全角。表情の名前に空白を含めない。
* 文字数（plan の target_chars）は、台詞・心の声・地の文の本文だけを数える（`@` の行、場面の区切り、表示名、表情を数えない）。
* 解析できない行は無い：`@` で始まり既知の命令でない行、形の崩れた `@` の行は「解析の誤り」。`［` や `「` を含むが台詞の形でない行は、地の文として扱い、機械検査で WARNING にする（台詞の書き損じの可能性）。

## 2. characters/<ID>.yaml の拡張

```yaml
id: C001
name: 山田太郎
display_name: カイ        # 台本の台詞の頭に書く名前
expressions: [通常, 笑顔, 驚き, 怒り, 悲しみ]   # 先頭が既定の表情
```

* どちらも省略できる（小説の形式の作品では使わない）。台本の形式の作品では、plan の場面に登場する人物に `display_name` が無ければ draft の前に止める（ChapterError）。
* `expressions` が無い人物は、表情を検査しない（立ち絵の無い人物）。
* 規則表（2-D）に `display_name` と `expressions` を加える。

## 3. plan.yaml の拡張

```yaml
scenes:
  - id: S1
    ...
    background: 市場_昼        # 省略可。場面の最初の背景の指示
    extras: [門番]             # 省略可。名前のない端役の表示名
    choice:                    # 省略可。場面の最後の選択肢
      - {text: 一緒に市場を回る, goto: S2, set: [market_together]}
      - {text: 船を見に行く, goto: S3, set: []}
    next: S4                   # 省略可。choice が無い場面の次の場面（既定は plan の次の場面）
```

* 背景の名前の一覧を作品で持つか【決定 3】。

## 4. 機械検査（台本の形式の作品だけ）

draft Job では FAIL、validate では WARNING（今の場面の区切りと同じ扱い。phase2-plan §4）：

| name | 内容 |
|---|---|
| `script_syntax` | 解析の誤りが無い |
| `script_flow` | 選択肢・移動の行き先が plan の choice・next と一致する（§5） |

validate では WARNING（draft では止めない）：

| name | 内容 |
|---|---|
| `script_speakers` | 台詞の表示名が、その場面の plan の characters の表示名か extras にある |
| `script_expressions` | 表情が、その人物の expressions にある |
| `script_stage` | `@exit` した人物、まだ `@enter` していない人物が台詞を言っていない【決定 4】。`@enter`・`@face`・`@exit` の人物 ID が plan の場面の characters にある |
| `script_speaker_words` | 話者の台詞に、その人物の speech.forbidden の語が無い（今の `forbidden_words` は作品全体で禁止した語だけを見る。話者が分かるので人物ごとに見られる） |
| `script_suspicious_lines` | 台詞の書き損じらしい地の文（§1） |

* 一人称・呼び方は機械検査にしない：一人称の語（俺・僕・私…）は台詞の中で一人称以外にも使われる（「僕って言うな」など）ので、語の照合だけでは誤検出が多い。Claude の検査（2-D）のまま。ただし Claude に渡す資料で、話者が確定していることを伝える。

## 5. 分岐とフラグ（章の中で分かれて合流する）

### 5.1 場面のつながり（2-E4）

* 各場面の次は、`choice` があればその行き先、なければ `next`、それもなければ plan の次の場面。最後の場面は章の終わり。
* 制約（plan の semantics で検査）：
  - 行き先は plan にある場面で、**自分より後ろの場面**（ループを作らない。位置の順序 2-D を場面の番号で保つため）
  - すべての場面が先頭の場面から到達でき、すべての道が章の終わりに着く
  - 台本の各場面の最後の行が、plan の choice・next と一致する（`script_flow`）。choice の場面は `@choice`、next を書いた場面は `@goto`、どちらも無い場面は何も置かない

### 5.2 フラグ（2-E4）

* フラグは作品全体で一意な名前を持ち、`flags/registry.yaml` に登録する（Human が書く。保護対象。§15 の経路で変更）。各フラグは、名前、説明、立てる位置（章・場面・選択肢）を持つ。今は真偽値だけ（好感度のような数値は扱わない）。
* フラグを立てるのは選択肢だけ（plan の choice の `set`、台本の `+<フラグ>`）。一度立てたフラグは下ろさない。
* `@if` の条件は、フラグ1つか、その否定だけ（and・or・入れ子を作らない。書き分けの組み合わせが増えすぎないため）。
* 機械検査：
  - `script_flags`：`+<フラグ>`・`@if` のフラグが registry にある。`@if` のフラグが、この位置より前（前の章を含む）で立ちうる。`@if`・`@else`・`@endif` の対応が取れている（draft では FAIL）
* plan の Claude のプロンプト：選択肢とフラグは outline に書かれたものだけを作る。Claude が独断で選択肢やフラグを足さない。

### 5.3 フラグに結び付いた設定（2-F。ここでは方針だけ）

Human の決定（2026-10-09）：分岐の中で呼び方・伏線・知識が変わってよい。合流後は、フラグで台本を書き分ける。

* 2-F で決めること：
  - characters の changes、伏線の位置、knowledge に `when: <フラグ>` を持たせる形
  - 規則表（2-D）を、フラグの値ごとに計算する方法（例：`C002: {default: 美咲, when market_together: 君}`）。台本の `@if` の中では、そのフラグの値の表で照合する
  - summary・state_update で、フラグごとの出来事と変化を分けて記録する方法
  - 組み合わせが増えすぎないための制限（1つの章で扱うフラグの数など）
* 2-F までの扱い：分岐の中だけを通る場面に設定の変化（changes の from、伏線の位置、知識の追加）があれば、state_update の検査で WARNING にし、Human に「2-F まではフラグごとの設定を扱えない」ことを示す（止めはしない）。

## 6. AI への指示

* AGY の draft のプロンプトに、台本の形式（§1 の表）と、その章の場面のつながり（choice・next）を入れる。表示名・表情の一覧は規則表で渡す。
* Claude の integrity_review・writing_review のプロンプトに、台本の形式の読み方を足す。writing_review には、台詞の長さ（メッセージ窓）と、地の文の多さを見る観点を足すか【決定 5】。
* plan の Claude のプロンプトに、background・extras・choice・next の書き方を足す。分岐は outline に書かれたものだけを作り、Claude が独断で分岐を足さない。

## 7. 変えないもの

* 小説の形式の作品の動作（project.yaml の `text_format` で選ぶ。既定は novel）【決定 1】
* 状態遷移、Job の流れ、承認、merge
* 2-D の規則表・伏線の検査（台本の形式でもそのまま使う）

## 9. 決定を受けて詰めた点（docs/script-format.md と agy-instruction-2e.md に反映）

* **場面の始まりで背景と立ち絵を空にする。** 分岐から合流する場面で、どの道から来たかによって画面の状態が変わらないようにするため。各場面は `@bg` で始めるのが基本（無ければ WARNING）。
* `@if` の中に置けるのは、台詞・心の声・地の文・`@face` だけ。立ち絵や背景を条件で変えると、画面の状態が道ごとに分かれ、検査も組み合わせになるため。
* 選択肢が立てるフラグは1つまで（plan の choice の `flag`、台本の `+<フラグ>`）。
* `flags/registry.yaml` の各フラグは `name`・`description`・`notes`。立てる位置は plan の choice から分かるので登録しない。flags/ は保護対象に加える（AI が書き換えない）。
* 台詞の長さ（決定 5）は、writing_review ではなく**機械検査** `script_line_length` で見る（字数を数えるだけなので、Claude に頼むより確実）。上限は `rules/script.yaml` の `max_line_chars`（無ければ見ない）。
* 文字数（target_chars）は、台詞・心の声・地の文の本文だけを数える。draft Job では jobrunner の文字数の検査を使わず（target_chars を渡さない）、台本の本文で数えた `char_count` を extra_checks で出す。
