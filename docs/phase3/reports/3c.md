### 新規作成ファイル
1. **`src/novui/impactjob.py`**
   - `run_impact_job(settings, work, *, base: str, head: str, reason: str, job_id: str | None = None, claude_runner: ClaudeRunner = run_claude) -> tuple[dict[str, Any], list[dict], list[str]]`:
     - `base..head` 間の差分のうち、保護対象（`is_protected` かつ `.novui/` 配下でないファイル）の変更差分（unified diff）を抽出。
     - 保護対象の変更がなければ Job 記録を作らず `ValueError("no protected change between ...")` を送出。
     - Job 記録を作成（job_type: `impact_analysis`、chapter_id: None、base_commit: base）。
     - `analyze_impact` を呼び出して Claude による影響範囲分析を実行。
     - 失敗時（check FAIL または Claude 出力取得失敗）は Job を FAILED に遷移。
     - 成功時（affected 章がある場合）は各章に `mark_review_required`（code: `setting_changed`、detail: `<reason>: <affected reason>`）を設定。
     - Job を COMPLETED に遷移させ、check に `impact_affected`（PASS）および notes があれば `impact_notes`（WARNING）を記録。
     - `(job_record, affected, notes)` のタプルを返却。

2. **`src/novui/directedit.py`**
   - `direct_edit(settings, work, *, kind: str, note: str | None = None, run_impact: bool = True, claude_runner: ClaudeRunner = run_claude) -> dict[str, Any]`:
     - kind のバリデーション（`typo` または `content`）および main ブランチの検証。
     - `git status` による未コミット変更の検出（変更なし・削除検出時はエラー）。
     - 対象ファイルの検証:
       - 対象外ファイル（`.novui/`、`chapter.yaml`、`summary.yaml`、README 等）、安全でないパス、作業ブランチが存在する章のファイルを拒絶。
     - 内容の検証:
       - 各ファイルの YAML 構文、schema、semantics を検証。
       - draft.md は `check_scene_markers` で plan.yaml の場面構成との整合性を検証。
     - 章の状態遷移・要確認フラグ設定（kind == "content" 時のみ）:
       - draft.md 変更章: `next_chapter_state` で DRAFTED に遷移し、`review_marked`（code: `previous_chapter_changed`）を付与。後続章を要確認対象に追加。
       - plan.yaml 変更章: PLAN_APPROVED の場合は直接 PLANNED に更新。DRAFTED 以降の場合は状態は維持しつつ後続章を要確認対象に追加。
       - outline.md のみ変更章: 章状態・フラグは変更なし。
       - 要確認対象章: 作業ブランチがある章はコミット前にブランチ側へ `mark_review_required(..., branch_only=True)` を実行。作業ブランチがない章は main の chapter.yaml に `review_marked` を設定して同一コミットに含める。
     - 単一コミットの作成:
       - `NovUI-Edit: human-<kind>` trailer を付与して `commit_all` でコミット。
     - 影響範囲分析の実行:
       - 保護対象の変更が含まれており、かつ `run_impact=True` の場合に `run_impact_job` を実行。失敗時はコミットを維持しつつ `impact_error` にエラー詳細を記録。
   - `reopen_chapter(settings, work, chapter_id: str) -> dict[str, Any]`:
     - main の chapter.yaml が DRAFTED、作業ブランチなし、draft.md および plan.yaml が存在することを検証。
     - `create_job_worktree` で新規 Job 用作業ブランチと worktree を作成。
     - `collect_draft_context` でコンテキスト情報を収集。
     - Job 記録を作成（job_type: `draft`、needs_validation: False、reason: `reopened after human content edit`）し、COMPLETED に遷移。作業ブランチには何もコミットしない。
     - 一連の validate/skip-validation → state-update → approve-state → final-approve の通常フローに接続可能とする。

## 3. 指示どおりにできなかった点（理由とともに）

1. **`src/novui/finalize.py` の修正**
   - **理由**: 指示書第18行の書込み禁止範囲に `src/novui/finalize.py` が含まれていましたが、3-C3 の「これで validate（または skip-validation）→ state-update → approve-state → final-approve が今のコードのまま通ること（テストで確かめる）」を満たすにあたり、既存コードに不整合がありました。
   - `direct_edit(kind="content")` を行うと main 上の `chapter.yaml` に `review_required` が付与されます。その後 `reopen_chapter` して作業ブランチを作り、`review-done` でフラグを解消しても、既存の `finalize.py:287` は `main_meta["review_required"] or branch_meta["review_required"]` と論理和をとっていたため、main 側の古いフラグが残存して `final_approve` が `InvalidTransition` でブロックされていました。
   - 一方で、作業ブランチ作成（`base_commit`）以降に main 側で新たに要確認フラグが立った場合はブロックする必要があります（既存テスト `test_finalize.py::test_review_required_blocks_final[main]` の仕様）。
   - そのため、作業ブランチ作成後に main 側で `chapter.yaml` が変更された場合のみ main 側のフラグを有効とし、それ以外は作業ブランチ側で解決された結果を尊重する判定ロジックへと修正しました。事前にユーザーへ状況を報告し、合意を得た上で実施しました。

2. **`reopen_chapter` における Job 状態遷移順**
   - **理由**: 指示書第100行では `QUEUED -> LOCK_ACQUIRED -> CLI_EXITED -> CHECK_PASSED（needs_validation=False）で COMPLETED` と例示されていましたが、NovUI の Job 状態機械（`src/novui/states.py`）では `LOCK_ACQUIRED` から直接 `CLI_EXITED` への遷移や `CLI_EXITED` から直接 `CHECK_PASSED` への遷移は未定義（`InvalidTransition`）です。
   - 指示書の「遷移の順が状態機械で許されなければ、許される最短の順を使い、報告に書く」に従い、状態機械で許可されている最短シーケンス `QUEUED -> LOCK_ACQUIRED -> CLI_STARTED -> CLI_EXITED -> CHECK_STARTED -> CHECK_PASSED -> COMPLETED` を使用しました。

## 4. 判断に迷った点

1. **`direct_edit` における plan.yaml 編集時の状態遷移**
   - 指示書において「state が PLAN_APPROVED なら PLANNED に（PLAN_REJECTED ではなく、直接 PLANNED に書く。遷移表に無いので、ここだけは next_chapter_state を使わず、理由をコメントに書く）」と指定されていました。
   - 状態機械 `next_chapter_state` はこの遷移を許可していないため、指示に従い辞書の直接書き換えを行い、意図が明確になるようコード内にコメントを記載しました。

2. **`direct_edit` 実行時の要確認フラグ付与と作業ブランチの扱い**
   - 指示書の「作業ブランチがある章は、commit の前に `mark_review_required(..., branch_only=True)`。作業ブランチの無い章は、`review_marked` で作った chapter.yaml を同じ commit に入れる」に従い、作業ブランチがある章に対しては main のコミットに含めず、作業ブランチ上に個別にコミットする方式としました。これにより main コミットが保護対象や編集対象ファイルのみでクリーンに保たれます。

3. **`run_impact_job` と `direct_edit` の連携におけるエラーハンドリング**
   - `run_impact_job` は保護対象の変更がない場合に `ValueError` を送出します。
   - `direct_edit` から呼び出す際には、変更ファイルに保護対象が含まれているか（`has_protected`）をあらかじめ確認し、保護対象変更が存在する場合にのみ `run_impact` を起動することで、正常な編集（保護対象外のみの編集）で `ValueError` が発生しないようにしました。
